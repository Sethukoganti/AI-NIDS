1. OVERVIEW — WHAT THIS PROJECT IS
================================================================================
AI-NIDS (AI-powered Network Intrusion Detection System) is a production-grade
security monitoring platform that analyzes network traffic flows using a
Random Forest classifier (100 trees, trained on CICIDS2017 dataset) to detect
attacks. It includes:

• Real-time (simulated) network traffic visualization with live packet flow
• AI-driven intrusion detection with SHAP explainability (feature importance)
• Full alert lifecycle management (New → Investigating → Confirmed / False Positive → Resolved)
• Role-Based Access Control (RBAC) with 2 roles: Admin (full control) and Analyst (monitoring only)
• Audit logging, notification system, investigation workspace, dataset pipeline
• ML model versioning, training run tracking, evaluation reporting
• Network status machine with automatic evaluation from traffic statistics

The system runs as two services: Backend (FastAPI on :8000) and Frontend (Vite/React on :5173).
Docker compose is provided for unified deployment.

6. ML / AI DETECTION ENGINE (RANDOM FOREST PIPELINE)
================================================================================
ALGORITHM: RandomForestClassifier (scikit-learn)
PARAMETERS: n_estimators=100, trained on CICIDS2017 subset
CLASSES (9): Normal Traffic, Bot, Brute Force, DDoS, DoS, Heartbleed,
              Infiltration, Port Scan, Web Attack
FEATURES (79): From CICIDS2017 feature set (packet lengths, durations,
               protocol, flow rates, byte counts, flag counts, etc.)

PIPELINE STAGES (documented in /api/model/architecture):
  1. Input validation (check for missing/extra columns, type validation)
  2. Feature extraction (79 features from flow records)
  3. Preprocessing (scaling, encoding — configured in preprocessing_config.json)
  4. Model inference (Random Forest prediction + probability)
  5. Risk scoring (combine confidence + feature deviation → risk_level)
  6. Alert generation (threshold comparison against detection_configuration)
  7. Explanation (TreeSHAP feature contributions — top 3 contributing features)
  8. Storage (predictions table + optional feature JSON)
  9. Feedback loop (model_version, evaluation, training_runs)

EVALUATION METRICS (real values from evaluation.json):
  Test accuracy: 99.5943% (0.995943)
  Macro F1: 0.981756 (0.9818)
  Test split: 30% (65,320 of ~217,734 total CICIDS2017 records)
  Per-class metrics available (precision, recall, f1, support)
  Confusion matrix available as 9x9 integer matrix
  Feature importance: horizontal bar chart (global + per-prediction)

PREDICTION OUTPUT FORMAT (every inference includes):
  • classification (Normal / Attack type)
  • attack_type (if attack: Bot / DDoS / DoS / etc.)
  • confidence (0.0 - 1.0, shown as %)
  • top_3_contributing_features (feature names + SHAP values)
  • timestamp (event_time or prediction created_at)
  • risk_level (low / medium / high / critical — from detection_configuration thresholds)
  • risk_score (0.0 - 1.0 computed from confidence + feature anomalies)
  • source_ip / destination_port / protocol / flow_duration / etc. (if available)

COLOR-CODING (confidence thresholds):
  Green (>90%) — high confidence
  Yellow (70-90%) — moderate confidence — review recommended
  Red (<70%) — low confidence — manual verification required

MODEL MANAGEMENT (Admin only):
  • Version registry (model_versions) — active / candidate / approved / retired
  • Deploy workflow: version must be registered + approved + confirmed
  • Training runs: dataset selection → configuration → evaluation → approval → deploy
  • Auto-retrain schedule (model_configuration.retraining_enabled + interval)
  • Model health: drift detection (prediction distribution shifts) — documented
    framework, not fully automated (requires admin review)

7. AUTHENTICATION & SECURITY HARDENING
================================================================================
AUTHENTICATION:
  • JWT (HS256) with issuer = APP_NAME, subject = user.id
  • Expiration: 480 minutes (8 hours) — configurable
  • Refresh: client re-logs in or uses /me to refresh user data
  • Password hashing: bcrypt (cost 12), max 72 bytes UTF-8 truncation
  • Session invalidation: access_reset_at stamps invalidate all tokens minted
    before reset (security.py enforces)
  • Logout: adds JWT jti to in-memory denylist (TokenDenylist, thread-safe)

RATE LIMITING (sliding window, in-memory — note: loses state on restart):
  Login: 10/minute per IP / per user
  Predict (analyze): 30/minute
  Upload (datasets): 20/minute
  Default (other /api/*): 300/minute
  Response: 429 with Retry-After + X-RateLimit-* headers

SECURITY HEADERS (SecurityMiddleware):
  X-Content-Type-Options: nosniff
  X-Frame-Options: SAMEORIGIN
  Referrer-Policy: no-referrer
  Permissions-Policy
  Cross-Origin-Resource-Policy: same-origin
  Cache-Control: no-store
  HSTS: enabled in production (ENVIRONMENT=production)

CSRF PROTECTION: Not explicitly implemented (token-based auth with Bearer header
                is the primary mechanism). Forms use JSON + Authorization header,
                which prevents traditional CSRF. Recommended: add CSRF token for
                cookie-based sessions if added.

INPUT SANITIZATION (backend):
  • All user inputs validated by Pydantic schemas (LoginRequest, UserCreateRequest,
    AlertUpdateRequest, ConfigUpdateRequest, etc.)
  • SQLAlchemy ORM with parameterized queries (no raw SQL injection risk)
  • File upload validation: content type whitelist, size limit (25MB default),
    filename sanitization (no path traversal — path containment check in download)
  • XSS prevented: JSON responses, no HTML interpolation of user data
  • File upload paths contained within upload_dir (download endpoint verifies)

CORS (properly configured):
  Origins from .env (localhost:5173, 127.0.0.1:5173, localhost:4173)
  Regex for https://*.eb.app and http://localhost/127.0.0.1
  Credentials: true
  Methods: GET, POST, PATCH, DELETE, OPTIONS
  Headers: Authorization, Content-Type, X-Request-ID

AUDIT LOGGING (append-only, tamper-resistant design):
  Every action recorded: user_id, user_email, user_role, action, category,
  resource, previous_value/new_value JSON, result (success/failed),
  detail JSON, ip_address, user_agent, timestamp
  Categories: auth, user, dataset, analysis, alert, investigation, model,
             system, network, audit
  Indexes on user+created, category+created for fast filtering
  Retention: audit_retention_days (default 730 = 2 years) from system_configuration
  Export: PDF / CSV available via /api/admin/audit-logs

ACCOUNT LOCKOUT (system_configuration):
  max_failed_logins (default 10) within window — enforced at login endpoint
  lockout_minutes (default 15) — enforced by tracking failed attempts
  Note: current implementation uses rate limiting (10/min) rather than
  persistent account-level lockout. Recommendation: add failed_attempts
  tracking to users table for true lockout.

PASSWORD POLICY (system_configuration):
  password_min_length (default 8)
  enforce_strong_password (default true — requires letters + numbers)
  Note: current login validates against stored hash only; no explicit
  complexity check at creation (UserCreateRequest has basic validator).
  Recommendation: strengthen UserCreateRequest validation.

8. ALERT & NOTIFICATION SYSTEM
================================================================================
ALERT LIFECYCLE STATUS FLOW:
  New → Acknowledged → Under Investigation / Confirmed Threat / False Positive → Resolved

Every status change logs: user, timestamp, optional note.
SLA timer: time since creation displayed in alert list / detail.
Auto-escalation: critical alerts unresolved after escalate_after_minutes
                 (default 30) → notify admins + increase severity.

ALERT GENERATION (auto):
  • AI detects attack above confidence threshold (min_confidence_to_alert)
  • Custom rules triggered (detection_configuration + risk_service rules)
  • System issues: model drift, high resource usage, monitoring downtime
  • Deduplication: duplicate_suppression (aggregate within duplicate_window_seconds,
    default 300 = 5 minutes) — prevents spam for same IP/attack

ALERT DETAILS (per alert):
  • Source IP, Destination IP, Protocol, Port, Attack Type, Severity
  • AI Confidence Score (0-100%), Risk Score (0-1.0)
  • Timestamp, Status, Message, Notes
  • Investigation link (if created)
  • Prediction link (to flow record)

NOTIFICATIONS (in-app + configurable):
  • Notification feed: severity/category-filtered, read/unread tracking
  • Severity levels: info, warning, critical
  • Categories: general, alert, investigation, model, system, user
  • Target: role-based or specific user
  • Email notifications: notify_email from system_configuration
  • Webhook: notify_webhook_url
  • Digest interval: notification_digest_minutes (default 60)

NOTIFICATION PREFERENCES:
  • Admin configures globally (system_configuration.notify_severities,
    notify_admins_on_critical, notifications_enabled)
  • Analyst can mute non-critical (not fully implemented — recommend adding
    per-user preferences table or JSON column)

16. KNOWN LIMITATIONS & RECOMMENDED NEXT STEPS
================================================================================
LIMITATIONS (functional, not broken):
  • Rate limit state is in-memory only — lost on restart / not shared across
    uvicorn workers. Recommend Redis for production multi-worker.
  • Account lockout is rate-based (10/min login) rather than persistent
    failed-attempt tracking. Recommend adding failed_attempts to users table.
  • Some notification/investigation analyst routes use P_ALERTS_VIEW instead
    of P_NOTIFICATIONS_VIEW / P_INVESTIGATIONS_NOTES (minor inconsistency).
  • Some dataset schemas use mutable defaults (attack_categories=[] etc.) —
    Pydantic v2 handles correctly but should use default_factory.
  • Background jobs (reports, retraining, cleanup) not fully automated —
    framework exists but requires scheduler (celery/rq/APScheduler).
  • Training run listing / creation routes partially missing — schema exists
    but only deploy route exposed. Recommend completing model registry.
  • Report generation uses browser print/download rather than server-side
    PDF rendering (weasyprint / wkhtmltopdf) — sufficient for current needs.
  • IP reputation / geolocation data referenced in config but not fully
    implemented (requires external service or database table).

RECOMMENDED NEXT STEPS (in priority order):
  1. Add Redis for rate limits / session state (production multi-worker)
  2. Complete model registry routes (list versions, create training runs)
  3. Add background job scheduler (reports, retraining, log archival)
  4. Strengthen UserCreateRequest validation (complexity rules)
  5. Add persistent account lockout tracking (users.failed_attempts)
  6. Implement server-side PDF report generation (weasyprint)
  7. Add IP reputation table / external lookup (configurable)
  8. Add per-user notification preferences (mute settings)
  9. Add WebSocket / SSE for true real-time traffic (currently simulated)
  10. Add database backup / restore scripts (data protection)
